# Socket(套接字)

## Socket编程

socket相关属性:
- 文件描述符：标识套接字在操作系统中的唯一标识
- 地址族: IPv4, IPv6等
- 类型: 流式套接字用于可靠连接通信，数据报套接字用于无连接的不可靠通信
- 协议：TCP, UDP
- 本地地址：套接字绑定的本地IP地址和端口。用于接收传入的连接请求或者数据
- 对端地址：与套接字建立连接的远程主机的IP和端口
- 状态：listening, connected, closed
- 发送缓冲区
- 接收缓冲区

### server端(创建监听socket)
- 创建监听socket
  - listenfd = socket(domain: AF_INET, type: SOCK_STREAM, protocol: 0);
- 设置socket
  - 设置地址复用
    - setsockopt(listenfd, SO_REUSEADDR)
    - 套接字关闭后允许立即重新使用相同的地址和端口，允许套接字绑定到一个之前使用过的地址和端口
    - 默认情况下，套接字关闭后，操作系统会保留一段时间处理可能仍然在网络中传输的延迟数据包
- 绑定监听地址
  - bind(listenfd, addr)
- 开始监听
  - listen(listenfd)
- 等待连接请求，三次握手
  - connfd = accept(listenfd)
    - 会创建a new onnected socket, and returns a new file descriptor referring to that socket
    - 新套接字的本地地址和端口与服务器套接字(监听套接字)相同：新套接字会继承服务器套接字的本地地址和端口
    - 新套接字的对端地址和端口与客户端发起连接的套接字相同
- 设置新的connfd
  - ioctl(fd, request: FIONBIO, &flags); // 设置非阻塞

### client端

- 创建socket: fd = socket()
- 尝试连接: ret = connect(fd, addr)

### 连接
服务端监听，客户端尝试连接，成功后会建立一条连接(如TCP连接)。
一条连接对应client端和server端的两个socket. 使用这两个socket进行网络通信。
{protocol, src addr, src port, dest addr, dest port}: {TCP, 127.0.0.2, 1234, 127.0.0.1, 80}

# Socket状态

两种关闭状态:
- 全关闭：close(fd)
- 半关闭：shutdown(fd, WR)，不可写，可读

close(fd)后本端读写fd报错: errno = 9(EBADF), Bad File Descriptor
close(fd)后对端写数据报错: errno = 104(ECONNRESET), connection reset by peer

读写失败时，若errno是如下两种，重试即可:
- EINTR: retry at once
- EAGAIN: retry next time

向收到RST的socket读写数据，会产生SIGPIPE信号，默认情况下会终止整个程序;
设置忽略SIGPIPE后，向收到RST的socket读写数据会返回-1，并置errno=EPIPE;

怎么感知socket已关闭或reset:
- read()返回0，表示对端关闭了写，通过close或shutdown
- read()返回-1，且errno不是EINTR或EAGAIN。表示socket收到了reset，如对端进程直接退出（EPIPE）；或表示本端已执行close（EBADF）
- write()返回0，表示写满了
- write()返回-1，且errno不是EINTR或EAGIN。表示socket收到了reset，如对端进程直接退出（EPIPE）；或表示对端已经close了连接（ECONNRESET）；或表示本端已执行close（EBADF）

# TCP网络链路

一个数据包从用户空间发出，到对端接收，分为两大部分: 发送端和接收端。

## 发送端

1. 用户空间应用程序
int len = send(socket_fd, message, strlen(message), 0);
send系统调用：将指向数据的指针和长度传递给操作系统内核。

2. 用户空间 -> 内核空间的切换
当 send 被调用时，会发生一次从用户态到内核态的切换。CPU开始执行操作系统内核的代码。 

3. 内核空间: Socket发送缓冲区
- 在内核中，每个Socket都有一个专属的 发送缓冲区。这是一个由内核管理的内存区域。
- send 系统调用的核心工作，就是将数据从用户空间提供的缓冲区，复制到这个内核的发送缓冲区中。
- send 的返回值：它返回的是实际被复制到发送缓冲区的字节数，而不代表数据已经发送到网络或对端。
  - 如果发送缓冲区空间充足，send 会立即返回，表示所有数据都已放入缓冲区。
  - 如果发送缓冲区已满（可能是因为网络拥堵，对端接收慢），send 调用可能会阻塞，直到有足够的空间容纳部分或全部数据。使用 fcntl 设置 O_NONBLOCK 标志可以使其变为非阻塞，立即返回错误 EAGAIN 或 EWOULDBLOCK。

从应用程序的角度看，数据已经“发送出去了”，但实际上它才刚刚进入内核的“待发队列”。后续的流程完全由操作系统内核异步处理。

4. 传输层 - TCP协议处理
- 内核中的TCP协议栈会从发送缓冲区中取出数据。
- 它负责将数据流分割成符合MSS 的TCP段。
- 为每个TCP段添加TCP头部（包括源/目标端口、序列号、确认号、窗口大小等）。
- 如果开启了Nagle算法（默认），可能会合并多个小数据包后再发送。

5. 网络层 - IP协议处理
- TCP段被传递给IP层。
- IP层添加IP头部（包括源/目标IP地址、TTL等），形成IP数据包。
- 根据系统的路由表，决定这个包应该从哪个网络接口发出。

6. 数据链路层 & 物理层
- IP数据包被加上以太网头部（MAC地址等），形成帧。
- 通过网卡驱动程序，数据帧被放入网卡的硬件发送队列。
- 网卡通过DMA方式将数据从主内存直接读取到其缓存中，然后将其转换成电信号或光信号，通过网线/光纤发送到网络中。

## 接收端

1. 物理层 & 数据链路层
- 网卡接收到信号，将其转换回数字数据。
- 如果目标MAC地址与自己的匹配，网卡会通过中断通知CPU。
- 驱动程序处理中断，并通过DMA将数据包放入内核内存中。

2. 网络层 - IP协议处理
- 内核的IP层检查IP头部的完整性和目标IP地址。
- 如果匹配，剥离IP头部，将载荷（TCP段）向上传递给传输层（TCP协议栈）。
 
3. 传输层 - TCP协议处理
- TCP协议栈处理TCP头部。
- 检查序列号、校验和等，确保数据正确。
- 如果一切正常，它会发送一个 **ACK确认** 给发送端。
- 然后，数据被按照正确的序列号重新组装，准备交付给应用程序。

4. 内核空间 - Socket接收缓冲区
- 重新组装好的、正确的数据流被放置到与对应Socket关联的接收缓冲区中。这也是一个由内核管理的内存区域。

5. 内核空间 → 用户空间的切换
- 在接收端的应用程序中，调用 recv（或 read, recvfrom 等）。
- 系统调用会导致从用户态切换到内核态。
- recv 的核心工作是将数据从内核的接收缓冲区复制到应用程序提供的用户空间缓冲区。

6. 用户空间应用程序
- recv 调用返回，携带返回值（实际读取到的字节数）。
- 数据现在位于 buffer 中，应用程序可以处理这些数据了。

## 总结

Socket发送缓冲区：解耦了应用程序的写入速度和网络的发送速度。它使得 send 可以快速返回，提高了应用程序的响应性，同时允许TCP进行流量控制、拥塞控制和数据重传。
Socket接收缓冲区：解耦了网络的送达速度和应用程序的读取速度。它缓存先到达的数据，等待应用程序来读取，避免了因为应用程序来不及处理而丢弃数据包。

# RDMA

## RDMA概念
Remote Direct Memory Access。允许一台计算机直接访问另一台计算机的内存，而不需要对方操作系统的介入。
可以理解为网络版的DMA。在单机内部，硬件（如网卡、磁盘控制器）可以通过DMA技术直接与内存交换数据，而无需CPU参与。RDMA将这一理念扩展到了网络之间。

## 核心思想和终极目标

RDMA的终极目标是 “零拷贝” 和 “内核旁路” ，从而实现极高的吞吐量和极低的延迟。它要解决传统网络通信（如TCP/IP）的瓶颈。
传统TCP/IP通信的数据路径非常长，需要经历多次上下文切换和数据拷贝，这导致了较高的延迟和CPU开销。
而RDMA通过其内核旁路 和零拷贝 的特性，建立了一条“高速公路”，让数据直接从用户应用程序的缓冲区传输到远端应用程序的缓冲区。

## RDMA 的核心特性与优势
- 内核旁路
  - 应用程序可以直接从用户空间对RDMA网卡进行操作，无需将控制流切换到内核态。这消除了上下文切换的开销。
- 零拷贝
  - 数据不需要在用户空间和内核空间之间来回拷贝。发送数据时，网卡直接从用户缓冲区读取；接收数据时，网卡直接写入用户缓冲区。
- CPU 卸载
  - 传输协议（包括数据分割、重组、确认、重传等）完全由RDMA网卡上的硬件处理，CPU几乎不参与数据传输过程。释放了宝贵的CPU资源给应用程序本身。
- 基于消息的事务模型
  - RDMA提供了一套基于消息的简洁操作原语，如SEND、RECEIVE、READ、WRITE等。

## RDMA操作原语
RDMA的核心是几种不同的通信操作：

1. SEND / RECEIVE
最类似于传统的Socket通信。
发送端发送消息，接收端必须提前发布一个接收请求来“迎接”这个消息。
数据缓冲区由接收方指定，但内容的解析需要双方应用层协议约定。

2. RDMA READ
主动“拉取”：本地端直接从远端节点的内存中读取数据。
远端节点对这次读取操作是不知情的（协议层面不知情，但建立连接时已授权）。
非常适合“请求-响应”模型，客户端直接读取服务器上的数据。

3. RDMA WRITE
主动“放置”：本地端直接将数据写入远端节点的内存中。
远端节点对这次写入操作也是不知情的。
非常适合“数据推送”或广播场景。

READ/WRITE是RDMA性能的极致体现，因为它们在通信过程中完全不需要远端的CPU参与。

## RDMA的传输服务类型

RDMA提供了不同质量的服务，以适应不同场景的需求：
1. 可靠连接
类似于TCP，保证数据包按顺序、无丢失地送达。最常用。

2. 不可靠连接
不保证数据包的顺序和送达，但数据包不会丢失。适用于音视频流等。

3. 可靠数据报
保证送达，但不保证顺序。较少使用。

4. 不可靠数据报
不保证顺序和送达，可能丢失。类似于UDP。

## RDMA的物理网络要求

RDMA最初依赖于特殊的InfiniBand 网络。为了在标准以太网上使用RDMA，又发展出了两种技术：

1. RoCE
全称 RDMA over Converged Ethernet。
版本有 RoCE v1（基于以太网链路层）和 RoCE v2（基于UDP/IP层，可路由）。
是目前最主流的方案，需要在数据中心级交换机上开启PFC 和ECN 等无损网络特性。

2. iWARP
全称 Internet Wide Area RDMA Protocol。
它基于TCP，理论上可以在任何IP网络上运行，但协议栈更复杂，硬件实现成本高，目前不如RoCE流行。
