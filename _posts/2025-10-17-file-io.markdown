# The Linux Storage Stack Diagram 概览  
  
上层：用户空间，是 I/O 的发起方。  
  
中间：内核空间，是处理 I/O 的核心，包括 VFS、文件系统、page cache, 块设备层等。  
  
下层：块设备（如 SSD/HDD），是 I/O 的最终目的地。  
  
## 1. Page Cache（页面缓存）  
图中，Page Cache 位于 VFS 和具体文件系统（如 ext4）右边，可以理解为在VFS+文件系统的下面，在 Block Layer 之上。它是整个文件 I/O 的 性能加速中心。  
  
作用：它是内存（RAM）的一部分，用于缓存磁盘上的文件数据。对文件的读写操作首先会作用在 Page Cache 上。  
  
读流程：当应用程序发起 read() 调用时：  
  
- VFS 和文件系统会先检查请求的数据页是否在 Page Cache 中。  
  
- 如果在（缓存命中），数据将直接从 Page Cache 拷贝到用户缓冲区，过程结束，极其快速。  
  
- 如果不在（缓存未命中），才会触发真正的磁盘 I/O，将数据从磁盘读入 Page Cache，然后再拷贝给用户。  
  
写流程：当应用程序发起 write() 调用时：  
  
- 数据被拷贝到 Page Cache 中相应的页面，该页面被标记为 “脏”。  
  
- 系统调用立即返回，写入在此时被认为“完成”。  
  
- 内核线程（如 pdflush）在后台将“脏”页异步地写回到磁盘。  
  
在图中的位置：所有通过文件系统的 I/O 请求，在到达块设备层之前，都会与 Page Cache 交互(Direct I/O除外)。它是 Buffer I/O（或称 Cached I/O）的基石。  
  
## 2. Buffer 的概念  
  
这是一个历史概念，在现代 Linux 中容易混淆。  
  
在 Linux 早期，有两个独立的缓存：Page Cache（用于文件数据）和 Buffer Cache（用于磁盘块）。  
  
现在它主要缓存的是 文件系统的元数据（如 inode table, bitmap。  
  
现在两者基本统一了。Page Cache 是主体。  
  
结论：现在谈论 Buffer I/O，通常指的就是经过 Page Cache 的 I/O。  
  
## 3. Direct I/O（直接 I/O）  
Direct I/O 在图中是一条 绕过 Page Cache 的路径。  
  
如何实现：应用程序在打开文件时使用 O_DIRECT 标志。  
  
在图中的路径：  
  
1. 用户空间的 write(data)。  
2. 系统调用 write()。  
3. VFS。  
4. 文件系统（如 ext4）。  
5. --> 关键点：此处不经过 Page Cache！  
6. 直接进入 Block Layer（I/O 调度）。  
7. 最终到达存储设备。  
  
优缺点：  
- 优点：避免了在 Page Cache 中进行两次拷贝（用户态<->内核态），适用于自知缓存策略的应用（如数据库）。保证写入不因缓存而延迟。  
- 缺点：每次读写都直接访问磁盘，速度慢，且失去了缓存带来的预读等性能优势。  
  
## 4. Sync（同步）  
Sync 操作关乎 数据持久化 的时机，它在图中作用于 Page Cache 和 Block Layer。  
  
什么是 Sync：强制将 Page Cache 中的“脏”页写入磁盘，并等待物理写入完成。  
  
相关系统调用：  
  
- fsync(fd)：刷新指定文件的所有数据和元数据到磁盘。  
- fdatasync(fd)：只刷新文件数据，必要时才刷新元数据（更高效）。  
- sync()：刷新所有“脏”页到磁盘。  
  
在图中的路径：  
  
- 应用程序调用 fsync()。  
- 调用穿过 VFS 和文件系统。  
- 文件系统向 Block Layer 提交该文件对应的所有“脏”页的写入请求。  
- 这些请求被 I/O 调度器处理。  
- 驱动程序通过 DMA 将数据写入磁盘。  
- 进程会阻塞，直到磁盘控制器返回写入完成的确认信号。  
  
与常规写操作的区别：没有 Sync 的 write() 只是写到 Page Cache 就返回，数据可能在几秒后才写入磁盘，存在断电丢失的风险。  
  
### 即使使用了 O_DIRECT，仍然需要 fsync 或 fdatasync  
  
O_DIRECT 和 fsync 解决的是不同层次的问题：  
- O_DIRECT：绕过 Page Cache  
- fsync：确保数据真正持久化到物理介质  
  
应用程序 -> O_DIRECT -> 文件系统 -> 块层 -> 设备驱动 -> 设备缓存 --**这需要fsync**--> 物理介质  
  
  
## 5. Mmap（内存映射）  
Mmap 在图中是一条从 用户空间 直接连接到 Page Cache 的 捷径。  
  
如何实现：应用程序使用 mmap() 系统调用，将文件的一部分直接映射到它的虚拟地址空间。  
  
在图中的路径：  
  
- mmap() 调用在进程的页表中创建映射，但此时并不加载数据。  
- 当进程首次访问该内存区域时，触发 缺页中断。  
- 内核处理中断，将文件的相应部分 按需 加载到 Page Cache 中。  
- 然后，内核更新进程的页表，使其 直接指向 Page Cache 中的物理页面。  
  
工作模式：  
- 读操作：进程直接从映射的内存地址读取，相当于直接从 Page Cache 读取。  
- 写操作：进程直接向映射的内存地址写入，相当于直接修改了 Page Cache，并标记为“脏”。后续的写回机制与普通 write() 相同。  
  
优缺点：  
  
- 优点：  
  - 零拷贝：避免了 read()/write() 所需的从内核缓冲区到用户缓冲区的数据拷贝。  
  - 随机访问友好：像操作内存一样操作大文件，非常高效。  
  
- 缺点：  
  - 内存映射和解除映射有开销。  
  - 对于小文件或顺序读写，优势不明显。  
  
## 总结：在图中看完整 I/O 流程  
以一个普通的 write() 调用为例，走一遍这张图：  
  
1. User Space：应用程序调用 write(fd, buf, size)。  
2. System Call Interface：调用 write() 系统调用，陷入内核。  
3. VFS：虚拟文件系统层，提供统一接口。根据 fd 找到对应的文件对象和文件系统。  
4. Filesystem（如 ext4）：文件系统处理写入逻辑（权限检查、计算文件偏移对应的块号等）。  
5. Page Cache：  
  - 找到或分配对应的缓存页。  
  - 将用户空间 buf 中的数据 拷贝 到这些缓存页中。  
  - 将这些页标记为 “脏”。  
  
6. (Return Path)：write() 系统调用返回。此时数据仍在内存中。  
7. (Async Writeback)：稍后，内核线程发现“脏”页，开始将它们写回。  
8. Block Layer：  
  - I/O Scheduling：对多个写入请求进行合并、排序。  
  - 将请求提交给设备驱动。  
  
9. SCSI Generic / Block Device Driver：驱动将请求转换为 SCSI/NVMe 命令。  
10. DMA：驱动程序设置 DMA，让磁盘控制器直接从 Page Cache 的内存中取数据。  
11. Block Device：数据被物理地写入 SSD/HDD。  
  
当使用 O_DIRECT 时，路径在步骤 4（文件系统）后，直接跳到步骤 8（块层），跳过了步骤 5 和 7。  
当使用 mmap 时，路径是从用户空间直接“触摸”到步骤 5（Page Cache），无需系统调用和拷贝。  
当调用 fsync 时，它会确保步骤 7 和 8-11 同步完成，然后才返回。  
  
# 异步IO  
  
传统 I/O 的瓶颈:  
1. 系统调用开销：每次 read/write 都需要进行一次昂贵的上下文切换（用户态<->内核态）。  
2. 数据拷贝开销：在 Page Cache 和用户缓冲区之间来回拷贝数据。  
3. 阻塞问题：  
- 同步 I/O：进程在系统调用处完全阻塞，直到 I/O 完成。  
- 半同步 I/O（如 O_DIRECT + 多线程）：虽然一个线程阻塞时其他线程可工作，但线程创建、调度、上下文切换成本高昂。  
  
真正的 异步 I/O 目标是：**应用程序发起一个 I/O 请求后立即返回，不会被阻塞，当 I/O 操作在底层完成时，应用程序能以某种方式被通知到。**  
  
## Linux AIO 的 I/O 流程  
  
Linux AIO 的设计目标是在 Block Layer 及以下实现真正的异步。它的路径在图中是一条 “绕道而行”的路径。  
  
写入流程  
应用程序发起一个异步写请求。  
  
1. User Space:  
应用程序准备一个 iocb 结构体，描述写操作（文件描述符、缓冲区、大小、偏移量等）。  
调用 io_submit 系统调用。  
  
2. System Call Interface:  
io_submit 系统调用陷入内核。  
  
3. VFS & Filesystem:  
请求穿过 VFS 和文件系统层。文件系统将文件的逻辑偏移转换为磁盘的块地址。  
  
4. 关键决策点：绕过 Page Cache:  
由于 Linux AIO 对 Buffer I/O 的支持很差，为了确保真正的异步，应用通常会使用 O_DIRECT。  
因此，数据不会进入 Page Cache。  
写入请求和用户缓冲区的数据描述被直接传递给异步 I/O 引擎。  
  
5. Block Layer:  
异步 I/O 引擎将请求提交到 Block Layer 的 I/O 调度队列。  
此时，io_submit 系统调用即可返回，告知应用程序“请求已提交”，但未完成。应用程序可以继续执行。  
  
6. Device Driver & Hardware:  
I/O 调度器对请求进行合并、排序。  
驱动将请求转换为 SCSI/NVMe 命令，通过 DMA 直接从用户空间的原始缓冲区将数据写入磁盘。  
整个过程，应用程序线程都不会阻塞等待磁盘写入。  
  
7. 完成通知:  
磁盘完成写入后，发送中断。  
内核的中断处理程序将完成信息放入 AIO 上下文。  
应用程序通过 io_getevents 系统调用轮询或等待这些完成事件。  
  
结合图的路径总结:  
User Space --(io_submit 系统调用)--> VFS --> Filesystem --(O_DIRECT 路径)--> Block Layer --> Device Driver --> Hardware  
  
核心特点：这是一条 “瘦路径”，它刻意避开了 Page Cache，以实现确定性。但这也导致了其功能受限和性能损失（失去缓存优势）。  
  
## io_uring的I/O流程  
  
io_uring 的革新在于它重新定义了用户态与内核态的通信方式。它在图中的路径覆盖了所有传统路径，但效率极高。  
  
写入流程:最高效的轮询模式。  
  
1. User Space:  
- 应用程序在用户内存中准备一个 提交队列条目，填写操作类型（如 IORING_OP_WRITE）、fd、缓冲区地址等。  
- 应用程序更新 SQ 的尾指针，这纯粹是用户空间的内存写操作。  
  
2. 零系统调用提交:  
- 内核有一个轮询线程，持续检查 SQ 的尾指针。  
- 当它发现新的请求时，主动地将其从 SQ 中取出。至此，请求已提交给内核，而应用程序未曾发出系统调用。  
  
3. VFS & Filesystem:  
- 内核线程带着请求进入 VFS 和文件系统层。文件系统执行路径查找、权限检查、逻辑块映射等。  
  
4. 灵活路径决策:  
  
- Case A: Buffer I/O（默认）:  
  - 请求进入 Page Cache。数据从用户缓冲区拷贝到 Page Cache 的页面中，页面被标记为“脏”。  
  - 此时，从应用程序视角，写入“已完成”。后续的脏页回写是内核后台任务的责任，与本次请求异步。  
  
- Case B: Direct I/O（指定了 O_DIRECT）:  
  - 请求绕过 Page Cache，直接进入 Block Layer。通过 DMA 将用户缓冲区数据写入磁盘。  
  
5. Block Layer & Below:  
- 对于 Case A，脏页回写由后台线程触发，进入 Block Layer。  
- 对于 Case B，请求直接进入 Block Layer。  
- 后续流程与常规 I/O 一致：I/O 调度 -> 驱动 -> DMA -> 磁盘。  
  
6. 完成通知:  
- 当 I/O 操作真正完成时（数据已写入 Page Cache 或 物理磁盘），内核将一个 完成队列条目 放入 CQ。  
- 应用程序在用户空间轮询 CQ，读取结果。再次无需系统调用。  
  
在图中的路径总结  
io_uring 的路径是多路并行的，它复用了整个 Linux Storage Stack：  
  
- 对于 Buffer I/O:  
  - User Space --(共享内存)--> VFS --> Filesystem --> Page Cache ...(异步回写)...> Block Layer --> ...  
  
- 对于 Direct I/O:  
  - User Space --(共享内存)--> VFS --> Filesystem --> Block Layer --> Device Driver --> Hardware  
  
核心特点：这是一条 “胖而快”的路径。它不回避栈的任何部分，而是通过消除系统调用和共享内存这两个最昂贵的开销，让整个栈都能以最高的效率运行。
