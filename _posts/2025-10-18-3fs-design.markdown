# Desion and implementation  
四个组件：  
- cluster mgr  
  - handles membership changes and distributes cluster configuration to other services and clients.  
- metadata service  
  - 发送心跳给mgr  
  - implement the file system semantics.  
  - stateless. file metadata存储在事务kv(eg. FoundationDB)  
- storage service  
  - 发送心跳给mgr  
  - 管理local ssds, 提供chunk(本文中的chunk概念为block, 非GFS中的chunk)访问接口  
  - Chain Replication with Apportioned Queries (CRAQ) to ensure strong consistency.  
  - write-all-read-any  
- clien  
  - FUSE client and native client. Most applications use FUSE client, which has a low adoption barrier. Performance-critical applications are integrated with the native client.  
  - 大多数应用使用FUSE client: 易于使用。  
  - 性能敏感应用使用native client.  
  
连接使用RDMA, InfiniBand or RoCE  
  
# File system interfaces  
  
对象存储对数据分析和机器学习越来越流行。但，文件系统语义(file system semantics)和统一的命名空间(unified namespace), 文件被目录管理提供更大的灵活性和可应用性。  
  
- Atomic directory manipulation  
  - 文件以及目录操作比对象存储更丰富，包括move, delete等  
- Symbolic and hard links  
- Familiar interface  
  
## Limitations of FUSE  
  
FUSE 的全称是 Filesystem in Userspace。它是一种允许我们在用户空间（而非操作系统内核）中实现文件系统的框架。  
  
传统操作系统中，文件系统（如 ext4、NTFS）是作为内核模块实现的。这意味着开发文件系统需要深入的内核编程知识，并且一个微小的错误就可能导致整个系统崩溃。  
  
FUSE 彻底改变了这一点。它通过一个位于内核的FUSE 内核模块作为代理或桥梁。这个模块会处理所有来自应用程序的常规文件操作请求（如 open、read、write），然后将这些请求转发给一个在用户空间中运行的守护进程。这个用户空间的进程才是真正实现文件系统逻辑的地方。  
  
### FUSE 的工作流程：  
  
![](https://chenghua-root.github.io/images/3fs-design-fuse.png)  
  
1. 应用程序（如 cat file.txt）向 VFS 发起一个标准文件操作请求。  
2. VFS 将该请求路由到 FUSE 内核模块。  
3. FUSE 内核模块 通过一个特殊的设备（/dev/fuse）将请求（包括操作命令和任何必要的数据，如文件路径、偏移量等）排队，并发送给用户空间的 FUSE 守护进程。  
4. FUSE 守护进程 接收到请求。这个进程包含了开发者自定义的文件系统逻辑。它可能会：  
  - 通过网络协议（如 SFTP、S3）从远程服务器读取数据。  
  - 从 ZIP 压缩包中提取文件。  
  - 根据自定义逻辑生成文件内容。  
  
5. 守护进程处理完请求后，将结果（数据或错误码，如 "文件未找到"）通过相同的 dev/fuse 通道返回给 FUSE 内核模块。  
6. FUSE 内核模块 将结果返回给 VFS，最终由 VFS 将结果送达原始应用程序。  
  
对于应用程序来说，它感觉自己只是在与一个普通的本地文件系统交互，完全不知道背后复杂的 FUSE 机制。  
  
### FUSE 的主要优势  
1. 安全性与稳定性：  
  - 由于文件系统逻辑运行在用户空间，即使它发生崩溃（ Segmentation Fault），也只会影响该守护进程本身，而不会导致整个操作系统内核崩溃。  
2. 开发便捷性：  
  - 开发者可以使用任何熟悉的编程语言（如 C、C++、Python、Go、Rust）来开发文件系统，无需掌握复杂的内核编程技巧。调试也变得和调试普通应用程序一样简单。  
3. 灵活性与创新性：  
  - FUSE 极大地降低了文件系统开发的门槛，催生了许多新颖的文件系统应用。  
  
### FUSE 的常见应用场景  
- 网络文件系统： 如 SSHFS（通过 SSH 连接挂载远程目录），将云存储（如 Amazon S3, Google Drive）挂载为本地文件夹的工具（如 rclone, s3fs）。  
- 加密文件系统： 如 gocryptfs、EncFS，它们将加密的文件数据存储在磁盘上，但在用户访问时动态地解密并提供明文视图。  
- 归档文件系统： 如 archivemount，可以直接将 tar、zip 等压缩包挂载为一个文件夹，像浏览普通目录一样访问其中的文件，无需手动解压。  
  
- 特殊用途文件系统：  
  - procfs/sysfs： Linux 系统本身就用类似 FUSE 的理念（虽然是在内核实现）来提供进程和系统信息视图。  
  - **FUSE 作为 API： 一些分布式存储系统（如 GlusterFS）使用 FUSE 客户端来提供 POSIX 文件接口。**  
  
### FUSE 的性能局限性  
FUSE 并非完美，其架构也带来了一些性能开销：  
  
1. 上下文切换与内存拷贝开销：  
每次 I/O 操作都需要在内核空间和用户空间之间进行多次切换和数据拷贝，这消耗了 CPU 和内存带宽，增加了延迟。  
2. 锁竞争：  
在高并发场景下，FUSE 内核模块中的请求队列可能成为瓶颈。多个线程争夺队列锁（spinlock）会导致 CPU 时间浪费在等待上，而不是处理 I/O，从而限制了性能的扩展性。  
3. 某些高级功能缺失：  
如原文提到的，在旧版本 Linux 内核中，FUSE 对同一文件的并发写入支持不佳，迫使应用采用变通方案。  
  
## Asynchronous zero-copy API  
  
文档描述了一种在 FUSE 框架内实现的高性能原生客户端设计方案，其核心是通过异步零拷贝 API 来解决 FUSE 的性能瓶颈。以下是对该方案的关键解读：  
  
### 核心设计理念  
在保留 FUSE 便于开发和维护的优势前提下，通过引入一个运行在 FUSE 守护进程内的原生客户端，绕开 FUSE 内核模块的性能瓶颈，直接为应用程序提供高性能 I/O 接口。  
  
1. 混合架构  
元数据操作(open/close/stat等)：仍通过标准 FUSE 路径处理，保证了 POSIX API 的兼容性，便于现有代码迁移。  
数据操作：通过新的原生客户端和异步零拷贝 API 处理，旨在实现高性能。  
  
2. 关键数据结构  
a) Iov - 零拷贝内存区域  
  
- 作用：一片在用户进程和原生客户端之间共享的大内存区域，用于数据读写。  
  
- 特点：  
  - 实现零拷贝，数据直接在共享内存中交换，避免了 FUSE 固有的内核与用户空间之间的内存拷贝开销。  
  - 由原生客户端管理 InfiniBand 内存注册，适用于 RDMA 等高速网络。  
  
- 工作流程：  
  - 读操作：数据从存储服务直接读入 Iov。  
  - 写操作：应用程序先将待写数据放入 Iov，再调用 API。  
  
b) Ior - 异步通信环  
  
- 作用：一个小型的共享环缓冲区，用于用户进程和原生客户端之间的异步通信。  
- 设计灵感：借鉴 Linux io_uring。  
  
- 工作模式：  
  - 入队：用户进程将 I/O 请求提交到 Ior。  
  - 出队与完成：原生客户端从 Ior 中取走请求并处理，完成后通知用户进程。  
  
- 并行处理：  
  - 请求按批次处理，批次大小由 io_depth 参数控制。  
  - 支持多个批次并行处理。  
  
- 多线程建议：  
  - 虽然单个 Ior 可被多线程共享，但仍建议为每个线程配置独立的 Ior，以避免锁竞争带来的性能损耗。  
  
### 性能优化策略  
1. 零拷贝传输  
通过 Iov 共享内存区域，彻底消除了 FUSE 最主要的内存拷贝开销。  
  
2. 异步与非阻塞  
通过 Ior 环实现请求的异步提交与完成通知，应用程序无需阻塞等待 I/O 完成。  
  
3. 请求批处理  
原生客户端内部的多线程会从各个 Ior 中批量获取 I/O 请求。  
  
优势：将大量的小 I/O 请求合并为批次，显著减少向存储服务发起的 RPC 调用次数，降低网络开销。  
  
4. 规避锁竞争  
为不同线程建议使用独立 Ior 环，避免了多线程在单一共享队列上的锁竞争，解决了标准 FUSE 扩展性差的问题。  
  
### 总结  
该设计是一个精妙的折中方案：  
- 它没有选择完全重写内核模块，从而规避了内核开发的高难度、高风险问题（如系统稳定性、调试困难、升级复杂）。  
- 它巧妙地利用了 FUSE 的框架来处理兼容性要求高的元数据操作。  
- 它在 FUSE 守护进程内部实现了一个高性能的“旁路”数据通道，通过引入共享内存和异步环等现代高性能 I/O 设计，精准地击中了传统 FUSE 在数据路径上的性能痛点。  
  
最终，这个原生客户端在保持 FUSE 的易用性和部署便利性的同时，为其赋予了接近内核级文件系统的 I/O 性能，特别适合需要处理大量小文件随机读写或高吞吐数据传输的场景。  
  
# File metadata store  
  
关于分布式文件系统 3FS 的元数据管理架构的详细描述。以下是对其核心设计的梳理与解读：  
  
## 核心架构总览  
3FS 的元数据管理采用清晰的分层与分离架构：  
  
数据分布：文件被分块(equally sized chunks)并条带化(stripes)存储在多个复制链(replication chains)上。  
元数据存储：所有元数据存储在 FoundationDB 这一分布式键值数据库中。  
  
服务层：元数据服务采用无状态设计，易于维护和扩展。  
  
## 1. 文件数据布局  
分块与条带化  
文件被切分为固定大小的块。  
  
这些块以条带化方式分布在多个复制链上。  
  
可配置性：用户可以在目录级别指定链表、块大小和条带大小。  
  
分配策略  
轮询选择：创建新文件时，从指定的链表中轮询选择连续的复制链。  
  
随机洗牌：使用随机种子对选中的链进行洗牌。  
  
目的：  
  
负载均衡：确保数据均匀分布在所有链和底层 SSD 上。  
  
确定性计算：客户端获取文件布局后，可自行计算任何数据块的 ID 和位置，使得数据读写操作无需元数据服务介入，实现短路读写。  
  
## 2. 元数据存储于 FoundationDB  
数据结构  
所有元数据以键值对形式存储，主要分为两类：  
  
A. Inode（索引节点）  
  
键结构："INOD"前缀 + 小端编码的64位全局唯一ID。  
  
小端编码使键分散，避免热点。  
  
值结构（按类型）：  
  
通用属性：所有者、权限、时间戳。  
  
文件特有：文件长度、块大小、使用的链表范围、洗牌种子。  
  
目录特有：父目录inode ID（用于检测目录移动时的循环）、子项默认布局配置。  
  
符号链接特有：目标路径。  
  
B. Directory Entry（目录项）  
  
键结构："DENT"前缀 + 父目录inode ID + 条目名称。  
  
值结构：目标inode ID 和 类型。  
  
优势：同一目录下的所有条目构成一个连续的键范围，使得目录列表操作可以通过高效的范围查询完成。  
  
事务与一致性  
读事务：用于 stat, lookup, listdir 等查询操作。  
  
写事务：用于 create, unlink, rename 等更新操作。  
  
冲突处理：FoundationDB 的可串行化快照隔离会跟踪读写集以检测冲突。发生冲突时，元数据服务会自动重试事务，从而在并行处理请求时保持强一致性。  
  
## 3. 动态文件属性管理  
这是针对特定工作负载（如AI训练）的优化，处理传统文件系统中棘手的并发与一致性问题。  
  
A. 文件会话与删除  
问题：传统文件系统需跟踪所有打开的文件描述符以延迟删除，这在打开大量文件的训练场景中负载过重。  
  
3FS 方案：  
  
只读文件：不跟踪文件描述符，简化设计。  
  
写入文件：为每个以写模式打开的文件描述符维护一个文件会话，防止删除时产生垃圾数据块。  
  
会话清理：通过周期性客户端活性检查，清理已离线客户端的会话，防止资源泄漏。  
  
B. 文件长度更新  
挑战：多客户端并发写入时，文件长度难以实时保持一致。  
  
解决方案：  
  
客户端周期性上报：客户端默认每5秒上报一次最大写入位置。  
  
服务端精确查询：在 close/fsync 时，通过查询存储服务获取最后一个数据块的ID和长度来确定精确长度。此操作开销较大。  
  
冲突缓解：使用会合哈希算法根据inode ID将文件长度更新任务分发到不同的元数据服务，减少事务冲突。  
  
性能优化：  
  
文件inode中存储了一个"可能使用的链数"的提示值。  
  
对于小文件，该值远小于总条带数（例如200）。  
  
该值从16开始，随着写入范围的扩大而倍增。  
  
效果：在更新小文件长度或删除小文件时，无需查询全部200条链，显著降低了I/O开销。  
  
## 总结与价值  
3FS 的元数据管理设计体现了以下几个关键工程思想：  
  
职责分离：将数据路径与元数据路径分离，将确定性计算下放到客户端，使系统更易扩展。  
  
权衡与优化：针对特定工作负载（大规模读密集型，如AI训练）做出明智的权衡，例如放弃只读文件的描述符跟踪，以换取可扩展性。  
  
利用底层数据库能力：充分运用 FoundationDB 的事务和冲突解决机制，简化了分布式一致性的实现。  
  
面向性能的启发式方法：使用"可能使用的链数"等启发式信息，在不牺牲正确性的前提下，大幅优化了常见场景（小文件操作）的性能。  
  
这套架构使得 3FS 能够支撑起生产环境中海量文件和高并发访问的需求，特别是在 AI 训练这类苛刻的场景下。  
  
# Chunk storage system  
  
## Data placemen  
  
每个file chunk(块)通过链式CRAQ方式写入。读可从任意链读取。  
  
一个chain包含多个target(ssd上的实体文件，类似百度沧海的volume)  
  
每个chain拥有一个版本号，由primary cluster manager进行维护。  
  
chain table:  
  - 由多个chain组成  
  - Each chain can be included in multiple chain tables. 因此target与chain table不是独占关系。  
  - The concept of chain table is created to let metadata service pick a table for each file and stripe file chunks across chains in the table.  
  
## Data replication  
CRAQ对读负载更友好。  
  
写入流程：  
1. 入流程版本检查：拒绝版本不匹配的写入请求。  
2. 数据拉取：通过 RDMA Read 将数据拉取到本地内存。  
3. 加锁与序列化：在链头获取块锁，确保对同一块的并发写入被序列化。  
4. 应用更新：读取已提交版本，应用更新，保存为待定版本。系统同时维护一个已提交版本和一个待定版本。  
5. 传播与提交：  
  - 如果不是链尾，则将写入请求转发给后继。  
  - 如果是链尾，则原子性地用待定版本替换已提交版本，并向前驱发送确认。  
6. 确认传播：前驱节点收到确认后，提交其待定版本，并继续向前传播确认，最后释放锁。  
  
读取流程:  
1. 如果只有已提交版本，直接返回。  
2. 如果存在待定版本，返回特殊状态码。客户端可选择：  
  - 等待后重试（获取已提交版本）。  
  - 发起宽松读请求（获取待定版本）。  
  
故障处理  
  - 链中节点故障时，集群管理器会更新链表（如将故障节点移至链尾）。  
  - 写入节点在收到新链表后，会持续重试转发，直至成功。  
  
## Failure detection  
集群管理器通过租约机制进行故障检测。  
  
**双状态模型**  
每个存储目标维护两种状态：  
  
A. 公共状态 - 对外公布，指导客户端和服务器的读写行为。  
  
  | 状态 | 可读 | 可写 | 描述 |  
  | -----  | ----  | ----  | ----  |  
  | serving	| ✅ | ✅ | 正常服务 |  
  | syncing	| ❌ | ✅ | 数据恢复中 |  
  | waiting	| ❌ | ❌ | 等待恢复 |  
  | lastsrv	| ❌ | ❌ | 故障前是唯一服务节点 |  
  | offline	| ❌ | ❌ | 已下线 |  
{: .tablelines}  
  
B. 本地状态 - 内部状态，作为触发公共状态转换的事件。  
- up-to-date：数据最新。  
- online：服务在线但目标未就绪。  
- offline：服务下线或介质故障。  
  
集群管理器根据预定义的状态转换表，定期扫描所有链，并基于本地状态更新目标的公共状态。状态变化会触发链版本号递增。  
  
## Data recovery  
  
恢复过程与正常活动重叠，旨在最小化服务中断。  
  
恢复流程  
1. 启动与标记：故障服务重启后，其所有目标被标记为 offline 并移至链尾。  
2. 写入驱动恢复：  
- 恢复期间，所有写入请求均为全块替换写入。  
- 持续的写入流将前驱的完整状态拷贝到恢复中的节点。  
  
3. 元数据同步：  
- 前驱向恢复节点发送 dump-chunkmeta 请求，获取其块元数据。  
- 前驱比较双方元数据，确定需要传输的块。  
  
4. 数据同步：  
- 对需要同步的块加锁。  
- 读取块内容，通过全块替换写入传输至恢复节点。  
- 解锁。  
  
5. 完成：所有块同步完成后，发送 sync-done 消息，恢复节点将本地状态更新为 up-to-date。  
  
## 块与元数据管理：本地存储引擎  
在每个 SSD 上，存储服务通过块引擎管理块数据。  
  
架构  
- 持久化存储：  
  - 数据文件：固定数量的文件，用于存储块数据。  
  - RocksDB 实例：用于存储块元数据和系统信息。  
- 内存结构：  
  - 元数据缓存：加速查询。  
  - 块分配器：快速分配新块。  
  
关键操作  
- get：通过哈希缓存获取块元数据，O(1) 复杂度。  
- update：采用写时复制，为新数据分配新块，旧块在所有引用释放前仍可读。  
- commit：通过 RocksDB 的写批次原子性更新元数据，并同步刷新缓存。  
  
物理块分配  
- 块大小：从 64KiB 到 64MiB，共11种规格（2的幂次）。  
- 资源池：为每种块大小维护一个包含256个物理文件的资源池。  
- 内存管理：使用位图在内存中跟踪物理块的使用状态。  
- 分配策略：优先重用已回收的块空间，减少碎片。空间不足时，使用 fallocate() 分配大块连续空间，一次性创建256个新块。  
  
写入优化  
- 常规写入：分配新物理块 -> 读取旧数据到缓冲区 -> 应用更新 -> 写入新块 -> 原子性更新元数据。  
- 追加优化：支持直接在现有块末尾原地追加数据，提升性能。  
  
这套精密的存储引擎设计，确保了在单个 SSD 节点上也能实现高效、可靠的块数据管理，为整个分布式存储系统的性能和一致性奠定了坚实基础。
